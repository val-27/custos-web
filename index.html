High-Performance, Zero-Copy Layer 7 Admission Control for AI Inference Traffic

Custos stops malicious gRPC requests before they reach AI inference backends. After Envoy reassembles the HTTP/2 request body (capped at 16 MiB per stream), Custos scans the binary Protobuf wire bytes in place over a shared Unix Domain Socket—rejecting structural and tensor-metadata exploits before the inference server deserializes the message or allocates buffers.

01 / Threat Model & Systems Boundaries

Application-Layer Protobuf Threat Taxonomy

Packet-level firewalls cannot parse multiplexed HTTP/2 gRPC streams, while L7 filters that deserialize entire Protobuf messages into heap objects add avoidable latency. Because Envoy reassembles HTTP/2 DATA frames into a contiguous buffer and passes the gRPC frame over an in-memory Unix Domain Socket, Custos inspects raw Protobuf wire tags directly in a single pass—blocking six classes of parser and runtime exploits without building an AST.

1. Protobuf Nesting & SGROUP Bombs CVE-2024-7254-Class

An attacker sends deeply nested length-delimited submessages (100s deep) or deprecated Protobuf v2 SGROUP (Wire Type 3) tags (the bug class illustrated by CVE-2024-7254) to bypass recursion counters and exhaust parser call stacks.

Runtime Impact: Recursive C++ and managed Protobuf parsers exhaust thread stack frames or stall CPU cores walking deeply nested trees.

✓ Defense: Iterative 16-frame stack array ([ScopeFrame; 16]) rejects depth ≥ 17 and immediately blocks Wire Types 3/4/6/7 & compressed frames (flag != 0x00).

In plain English

Picture a parcel with a smaller parcel inside it, and a smaller one inside that — hundreds deep. Each time the server opens one, it has to jot down where it was so it can find its way back out. Open enough of them and it runs out of notepad and crashes.

Custos doesn't open the parcels. It just counts them, and the moment it hits number 17 (or sees a disguised legacy box) it throws the whole thing in the bin.

2. Tensor Shape Overflows OOM / Integer Wrap

An attacker sends requests that claim the data is extremely large (like declaring a picture is "negative one" pixels or "a billion by a billion" in size), or uses numbers so big they wrap around to become small numbers.

Runtime Impact: The AI server wastes memory trying to allocate space for data that doesn't really exist and crashes.

✓ Defense: Custos multiplies the claimed size numbers before allowing them. If the size is bad or too large, the request is rejected.

In plain English

Before sending a picture, the request announces how big it is. A liar can claim it's minus one pixels wide, or a billion by a billion. The server believes the label, immediately tries to clear a shelf that enormous, and gets killed for hogging memory.

Custos does the multiplication first. If the claimed size isn't a sensible number, the request never reaches the shelf.

3. Malformed Varints Parser CPU Hang

Numbers in messages are sent in chunks. An attacker sends a chunk that says "there's more" but never sends the next piece, or sends more than 10 chunks when 10 is the limit.

Runtime Impact: The parser waits forever or runs forever trying to decode the number, freezing an entire AI server worker thread.

✓ Defense: Custos stops reading after 10 chunks and rejects the message if it's not complete by then.

In plain English

Big numbers get sent in small pieces, and every piece ends with "…and there's more coming". A troublemaker sends pieces that always say that and never finish the sentence. A naive reader waits forever, pinning a CPU core at 100%.

Custos knows a real number is never longer than 10 pieces, so it stops listening at the 11th and rejects the request.

4. Per-Input Shape & Buffer Parity KServe v2 Wire Invariant

An attacker declares a valid fixed-width tensor shape (e.g., [4, 3, 224, 224] FP32 = 2.41 MB), passing element-count ceilings, but supplies a truncated 64-byte raw_input_contents chunk, swaps multi-tensor chunks, omits payload bytes, or crafts an overrunning 4-byte BYTES length prefix. (Separately, NVIDIA's CVE-2025-23320 and CVE-2025-23334 advisories cover Python-backend shared-memory name disclosure on oversized payloads and subsequent shared-memory OOB read.)

Runtime Impact: Backends that bind input metadata to mismatched raw tensor chunks risk out-of-bounds buffer reads or unhandled runtime exceptions.

✓ Defense: Enforces 1-to-1 per-input parity between each InferInputTensor and its raw_input_contents[i] chunk (or inline InferTensorContents), plus exact 4-byte little-endian prefix walking for BYTES tensors.

In plain English

Imagine ordering a 24-pack of soda (a perfectly reasonable size), but the delivery box only has one can inside. If the warehouse robot blindly grabs 24 cans' worth of space off the conveyor belt, it ends up grabbing 23 cans belonging to the customer behind you.

Custos checks that the weight of every individual box matches its label before letting it inside—and walks the 4-byte length headers inside variable-length text boxes (BYTES tensors) without false alarms.

5. Shallow Unknown-Field & Packed-Tag Flood CVE-2022-1941-Class

Instead of nesting deeply, an attacker packs thousands of 2-byte unrecognized varint tags at root depth (D=0) or floods packed repeated fields—exercising the Protobuf parser resource-exhaustion bug class (CVE-2022-1941 in C++ protobuf-cpp, CVE-2021-22569 in protobuf-java).

Runtime Impact: Standard parsers accumulate unrecognized tags in an in-memory UnknownFieldSet or spend linear CPU decoding millions of unit-value dimensions.

✓ Defense: Enforces a strict 1,024-tag scan ceiling per message (covering both TLV tags and packed shape/contents varints) and never allocates an UnknownFieldSet.

In plain English

Instead of nesting boxes inside boxes, the attacker hands the clerk a single flat sheet covered in thousands of tiny nonsense sticky notes. A dutiful clerk files a separate manila folder for every sticky note they don't recognize, quickly filling the entire filing room.

Custos never creates folders for unknown notes, and if a form has more than 1,024 tags or dimensions total, it rejects it on the spot.

6. Shared-Memory Params & Admin RPCs CVE-2024-0088

Attackers either invoke administrative RPCs (SystemSharedMemoryRegister, RepositoryModelLoad) OR bypass header-only allowlists by injecting shared_memory_region, shared_memory_offset, and shared_memory_byte_size inside ModelInfer parameter maps (CVE-2024-0088: out-of-bounds offset and byte size relative to a registered shared-memory region).

Runtime Impact: Out-of-bounds shared-memory offset/size parameters allow reading or corrupting shared memory outside the registered region or loading unauthorized models.

✓ Defense: Dual-stage enforcement blocks admin RPC paths at RequestHeaders (403 Forbidden) AND scans ModelInfer parameter map keys in RequestBody to reject shared_memory_* injection (400 Bad Request).

In plain English

By default, Triton puts the customer service window (ModelInfer) and the staff-only control room door (RepositoryModelLoad, SystemSharedMemoryRegister) in the same hallway—and even lets normal forms sneak in staff-only memory pointers (shared_memory_offset).

Custos locks the staff-only doors at the header stage (403 Forbidden) and checks inside every normal inference form to block hidden shared_memory_* parameters before they reach Triton.

How we test Custos and how we know it works

We compare the same requests in three setups: with Custos, with the proxy only, and with no protection. We check that Custos lets normal requests through, blocks test attacks, and keeps the service working.

1. Does it block unsafe requests?

We send 39 test attacks. A good result blocks all 39. We also send 20 normal requests. A good result allows all 20. The goal is zero wrong blocks.

The safety table compares each result with the expected result. Green means it matched. Red means it did not.

2. Does the service keep working?

We send normal requests while attack requests arrive. We count normal replies that succeed. In the burst test, Custos served all 250 normal requests.

We also record failed requests and server errors. Fewer errors and more successful replies are better.

3. How much time does Custos add?

We measure the time from sending a request to getting its reply. The charts show the middle reply time and the slower replies.

We compare Custos with the proxy-only setup. This shows the extra time from the Custos check.

4. How does the work change with data size?

We test image requests from 1 to 16 images. The data grows from about 0.6 MB to 9.6 MB.

The green line shows Custos check time. The red line shows the time to read all data. A flat green line means the check time stayed about the same as the data grew.

How to read the measures

  • Response time: Time from request sent to reply received. Lower is faster.
  • P50, P90, P95, P99, P99.9, P99.99: These show how long different shares of requests took. P50 is the middle. P99 means 99 of 100 replies arrived by that time. P99.99 means 9,999 of 10,000 arrived by that time.
  • Requests per second: The client sets how many requests to send. The chart shows how many the setup completes. If it completes fewer, it cannot keep up.
  • False blocks: Normal requests that Custos blocked by mistake. Zero is the goal.
  • Attack blocks: Test attacks that Custos blocked. Blocking all test attacks is the goal.
  • Peak memory: The most memory used by the server, proxy, and Custos during a test.
  • Server result: Whether the server stayed healthy, slowed down, or failed during the test.

How the tests run

  • Normal test: Sends valid requests only.
  • Mixed test: Sends 94 normal requests and 6 test attacks for every 100 requests.
  • Burst test: Runs 500 requests at the same time. 90% are test attacks. 10% are normal requests.
  • Safety sweep: Sends each of the 59 test requests once through each setup. It checks each reply against the expected result.

The performance tests use the same hardware and run five times. The results table shows the average. In the normal and mixed tests, the client sends requests on a set schedule, even when replies are slow. The response-time measure includes time spent waiting for a reply. This helps us see delays that a slow server could otherwise hide. The page shows saved results, not live measurements.

How we reach the evaluation: Custos matched all 59 expected safety results. It allowed 20 normal requests and blocked 39 test attacks. During the burst test, all 250 normal requests succeeded. Their slowest 1 in 100 replies took 153 ms. The other setups took 511 to 518 ms. Custos check time stayed near 14 to 15 microseconds as image data grew from 0.6 to 9.6 MB. These results support Custos for these tests. They do not prove that every possible attack will be blocked. The tests set no single speed limit. Compare the added time with your needs.
